# Лабораторная работа № 6. Spring Security

Вариант 7 — «Военнослужащий».

## Цель работы

Добавить к веб-приложению аутентификацию пользователей с помощью Spring Security и разграничить доступ к страницам по ролям. Учётные записи хранятся в H2, пароли в базе представлены BCrypt-хешами; вход выполняется через стандартную форму и HTTP-сессию, без JWT.

## Архитектура проекта

- **Стек:** Java 25, Spring Boot 4.1.1, Maven, Spring MVC, Spring Data JPA, Hibernate ORM, Bean Validation, Thymeleaf и Spring Security.
- **СУБД:** H2 in-memory (`jdbc:h2:mem:lb3`). Hibernate создаёт таблицы при запуске (`spring.jpa.hibernate.ddl-auto=create-drop`), а `data.sql` добавляет исходные звания и пользователей. При перезапуске база создаётся заново.
- **Основные слои:**
  - **Model:** сущности `Serviceman`, `Address`, `MilitaryRank`, `User`; перечисление `Role` содержит роли пользователей.
  - **DTO:** `ServicemanForm`, `AddressForm`, `RankForm`, `SearchForm` принимают данные HTML-форм и параметры поиска.
  - **Controller:** `ServicemanController` обрабатывает список, поиск и добавление военнослужащих; `RankController` — список и добавление званий.
  - **Service:** `ServicemanService` ищет записи и сохраняет военнослужащего с адресом; `UserService` загружает учётную запись по логину для Spring Security.
  - **Repository:** `ServicemanRepository` выполняет JPQL-поиск; `MilitaryRankRepository` работает со званиями; `UserRepository` ищет пользователя по логину.
  - **View:** Thymeleaf-шаблоны `servicemen/list.html`, `servicemen/form.html`, `ranks.html`; стили находятся в `static/css/style.css`. Страницу `/login` по умолчанию формирует Spring Security.
  - **Security:** `SecurityConfig` настраивает правила доступа, стандартную форму входа и `BCryptPasswordEncoder`.

**Маршруты:**

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/` | Перенаправление на список военнослужащих |
| `GET` | `/servicemen` | Просмотр записей и результатов поиска |
| `GET` | `/servicemen/new` | Форма добавления военнослужащего; требуется `ADMIN` |
| `POST` | `/servicemen` | Проверка и сохранение военнослужащего с адресом; требуется `ADMIN` |
| `GET` | `/ranks` | Просмотр званий |
| `POST` | `/ranks` | Проверка и добавление звания; требуется `ADMIN` |

Просмотр страниц требует аутентификации. Операции добавления доступны только пользователю с ролью `ADMIN`.

### Описание моделей данных и DTO

**Сущности и роли:**

| Класс | Таблица | Данные |
|---|---|---|
| `Serviceman` | `servicemen` | Фамилия, имя, отчество, национальность, дата рождения, должность, ссылки на адрес и звание |
| `Address` | `addresses` | Почтовый индекс, страна, область, район, город, улица, дом и квартира |
| `MilitaryRank` | `military_ranks` | Название звания и обратная коллекция военнослужащих |
| `User` | `users` | Логин, BCrypt-хеш пароля и роль |

`Serviceman` связан с `Address` отношением один к одному: каждому военнослужащему соответствует отдельная адресная запись. Связь `Serviceman` — `MilitaryRank` является «многие к одному», а `MilitaryRank` содержит обратную коллекцию военнослужащих. `Role` реализует `GrantedAuthority` и задаёт значения `ROLE_USER` и `ROLE_ADMIN`. Идентификаторы сущностей генерируются базой данных.

| DTO | Назначение и данные |
|---|---|
| `ServicemanForm` | Персональные данные, должность, ID звания и вложенный объект `AddressForm` для создания военнослужащего |
| `AddressForm` | Поля адреса: индекс, страна, область, район, город, улица, дом, квартира |
| `RankForm` | Название добавляемого звания |
| `SearchForm` | Фильтры списка: фамилия, национальность, город, должность и ID звания |

`ServicemanForm` и вложенный `AddressForm` проверяются на заполненность и допустимую длину; дата рождения должна быть в прошлом, ID звания — положительным. `RankForm` проверяет название. `SearchForm` ограничивает длину текстовых фильтров и проверяет ID звания. Формы регистрации пользователя нет: учётные записи загружаются из `data.sql`.

### Описание реализованных мапперов

Отдельных классов-мапперов и MapStruct в проекте нет. Преобразование данных выполняется вручную в существующих слоях:

- `ServicemanService.create()` переносит значения из `ServicemanForm` и `AddressForm` в сущности `Serviceman` и `Address`, загружая `MilitaryRank` по ID.
- `RankController.create()` создаёт сущность `MilitaryRank` из `RankForm`.
- `UserService.loadUserByUsername()` преобразует найденную сущность `User` в `UserDetails` Spring Security с логином, хешем пароля и ролью.
- `ServicemanService.search()` очищает текстовые фильтры и передаёт их вместе с ID звания в репозиторий; отдельное преобразование сущностей для поиска не выполняется.

### Аутентификация и разграничение доступа

При запуске `data.sql` добавляет две учётные записи. В таблице `users` хранятся BCrypt-хеши, а для входа используются исходные пароли:

| Логин | Пароль | Роль |
|---|---|---|
| `user` | `password` | `ROLE_USER` |
| `admin` | `pass2` | `ROLE_ADMIN` |

`UserService` находит запись через `UserRepository`. Spring Security проверяет введённый пароль с помощью `BCryptPasswordEncoder`. После успешного входа используется HTTP-сессия. CSRF-защита оставлена в состоянии по умолчанию; формы Thymeleaf с `th:action` включают CSRF-поле. JWT и другие токены аутентификации не используются.

## Алгоритм работы

1. **Запуск и подготовка базы.** `Lb3Application` запускает Spring Boot. Hibernate создаёт таблицы `servicemen`, `addresses`, `military_ranks` и `users`; затем `data.sql` добавляет исходные звания и пользователей с BCrypt-хешами. Так как H2 работает in-memory с `create-drop`, при следующем запуске таблицы и эти записи создаются заново.
2. **Аутентификация.** При обращении к защищённой странице Spring Security показывает стандартную форму `/login`. `UserService` ищет логин в базе; кодировщик проверяет пароль. После успешного входа браузер использует сессию, а Spring Security применяет роль пользователя к защищённым операциям.
3. **Показ списка.** Запрос `/` перенаправляется на `/servicemen`. Контроллер передаёт параметры в `SearchForm`, проверяет их, загружает звания и получает записи через сервис и репозиторий.
4. **Поиск.** Пользователь отправляет GET-форму. Заполненные условия объединяются через `AND`; фамилия, город и должность ищутся по вхождению части строки, национальность — по полному совпадению без учёта регистра, звание — по ID. Текстовый поиск выполняется без учёта регистра. Символы `%` и `_` экранируются. Результаты сортируются по фамилии, имени и ID.
5. **Загрузка связанных данных.** JPQL-запрос использует `join fetch` для адреса и звания. Шаблон получает связанные данные до формирования HTML; `spring.jpa.open-in-view=false` закрывает JPA-контекст до отображения страницы.
6. **Открытие формы военнослужащего.** При GET `/servicemen/new` контроллер передаёт пустой `ServicemanForm` и список званий. Операция доступна роли `ADMIN`.
7. **Проверка и сохранение военнослужащего.** После POST `/servicemen` Spring связывает разрешённые поля с DTO и запускает Bean Validation. Контроллер дополнительно проверяет существование выбранного звания. Если ошибок нет, `ServicemanService` создаёт `Address` и `Serviceman`, устанавливает связи и сохраняет запись. После сохранения браузер перенаправляется на список.
8. **Добавление звания.** GET `/ranks` показывает список и форму. При POST `/ranks` контроллер проверяет название и отсутствие дубликата без учёта регистра, создаёт `MilitaryRank` и сохраняет её. Для добавления требуется роль `ADMIN`.
9. **Отображение результата и ошибок.** Thymeleaf формирует список через `th:each`, выводит значения через `th:text`, связывает поля через `th:field` и показывает ошибки через `th:errors`. При ошибках валидации форма возвращается с введёнными данными и сообщениями.
